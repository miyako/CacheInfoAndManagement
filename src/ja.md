# キャッシュの情報と管理

Thomas SCHLUMBERGER（4D France テクニカルサポートエンジニア）

テクニカルノート 25-02

## 概要

4Dのキャッシュは、作成・更新されたデータや、頻繁にクエリされるデータを保持するバッファーです。キャッシュは4Dエンジンの予約領域として動作しますが、そのパフォーマンスを最適化するために、キャッシュを操作するための設定とコマンドが用意されています。キャッシュのパフォーマンスは、サーバーの構成だけでなく、データベースの設計によっても左右されます。

## はじめに

本テクニカルノートでは、4Dにおけるキャッシュ設定の変遷を簡単に振り返り、サイズが固定か自動計算かにかかわらず最適化された、4Dエンジンによるキャッシュの管理方法を説明したうえで、キャッシュのパフォーマンスを向上させるために可能な操作を中心に解説します。いくつかの設定を変更することでキャッシュのサイズやフラッシュ頻度を調整でき、キャッシュの内容を操作するためのコマンドも用意されています。

本テクニカルノートでは、キャッシュとは何か、どのように進化してきたか、そしてキャッシュを操作するためにどのようなツールがあるかを説明します。

## キャッシュストレージとメモリストレージ

### キャッシュに移されて保存されるもの

キャッシュに保存されるのは、次の要素です：

- テーブル、フィールド、リレーション、インデックスなどのストラクチャー定義
- 開いているデータベースに関する一般情報（ファイルパス、プロパティなど）
- データファイルのアロケーションビットテーブル
- レコード、インデックス、BLOB、追加プロパティなどのアドレステーブル
- インデックスページ
- レコード
- BLOB（キャッシュに十分な空きがない場合は、代わりにメインメモリに割り当てられることがあります）
- 追加プロパティ
- シーケンス番号
- トランザクション
- セレクション
- セット
- ソート、先読み、バッファー付きディスク書き込みなどのための一時バッファー
- ストラクチャーオブジェクト（メソッド、フォームなど）

4Dは常にメモリを管理し、さまざまな種類のオブジェクトをやりくりして、内部アクセスをできるだけ効率的に保っています。

### キャッシュではなくメモリに保存されるもの

- 4D Webサーバーのキャッシュ（有効な場合。設定の「Web／オプション（I）」）：

![](fig-14)

- あらゆる種類のStorageの内容
- 有効なすべてのログ
- 開いているファイルなど、有効なすべてのOSキャッシュ

## 4Dはキャッシュをどのように管理しているか

この問いには、次のように答えることができます：「それは4Dにとって複雑で、非公開で、保護されたテーマであり、長年の改良と適応の成果です…」。

ログインのための認証情報を持つユーザーであっても、キャッシュに到達するまでには多くの層があることを考えてください。ユーザーが利用できるのは、キャッシュの設定といくつかのコマンドだけです。

![](fig-15)

### キャッシュの内部構成は公開されていません

- 機密情報の秘匿という当然の理由のため
- 将来の変更や最適化のため

### 覚えておくべきこと

起動時には、データのクエリや作成を一切おこなっていなくても、キャッシュは後のデータアクセス（およびストラクチャーやコードへのアクセス）のために、いくつかの要素を読み込みます。

4D/4D Serverは現在のキャッシュサイズと利用可能な空きメモリに適応しますが、現在のサイズがデータベースの用途に適しているかどうかを確認するのは、設計者または管理者の役目です。

新規プロジェクトでは、デフォルトで次の設定が適用されます（デザインモード向け）：

- 「起動時にキャッシュサイズを計算」がチェックされている

![](fig-16)

利用可能なメモリの50%をキャッシュに使用する設定であっても、また大容量のRAMがあっても、最大サイズは400 MBに設定されていることに注意してください。

データファイルが大きくなったときや、データベースを運用環境に配備するときは、この最大サイズの値を増やすことを忘れないでください。

4Dが新しいオブジェクトのためにキャッシュに空きを作る必要がある場合は、まずパージをおこなわなければなりません。

### 考慮すべき主な点

- 4DのACID準拠：ACID（原子性、一貫性、独立性、永続性）とは、エラーや停電などの不具合が起きてもデータの正当性を保証するために設計された、データベーストランザクションの特性の集合です。データベースでは、ACID特性を満たす一連の操作（多くの場合、データに対する単一の論理操作とみなされます）をトランザクションと呼びます。トランザクションは、多くの場合、複数のステートメントで構成されます。原子性は、各トランザクションが完全に成功するか完全に失敗するかのいずれかである単一の「単位」として扱われることを保証します。トランザクションを構成するステートメントのいずれかが完了しなかった場合、トランザクション全体が失敗し、データベースは変更されません。原子性を備えたシステムは、停電、エラー、クラッシュを含むあらゆる状況で原子性を保証しなければなりません。
- CRUD（作成、読み取り、更新、削除）：データが増えて古くなるにつれて、作成・更新・削除の操作の頻度は、読み取り操作に比べて相対的に低くなります。運用時のキャッシュの使われ方をシミュレーションするには、負荷テスト用に大規模なデータセットを作成する際に、CRUD操作の比率の変化を考慮することが重要です。そうすることで、大規模なデータベースの一般的な使用パターンをより正確に反映できます。

キャッシュは動的なリソースのように機能します。サーバーを再起動しなければ、接続ユーザーが最も頻繁にアクセスする内容を保存し続け、最も頻度の高いリクエストに対する応答性が高まります。

## 運用時のキャッシュを含む設定ファイル

データベースにキャッシュ設定を適用すると（ストラクチャー設定の「データベース／メモリ」）、その設定はデフォルトでローカルに適用され、そのコンピューター用の設定になります。これは主に、デザイン時のテストやローカルでの負荷テストに適したものです。

既存のデータファイルごとに異なる設定でデータベースを配備する必要がある場合は、設定の1つをチェックする必要があります（ストラクチャー設定の「セキュリティ／ユーザー設定を有効にする」）：

![](fig-17)

「ユーザー設定を有効にする」をチェックすると、データベースの再起動時に、設定用の新しいポップアップが表示されます：

![](fig-18)

「ユーザー設定」または「データファイルのユーザー設定」で設定を変更すると、新しい設定ファイル「settings.4DSettings」が「Settings」フォルダーに追加または更新されます：

たとえば、キャッシュの設定をいくつか変更した場合：

```xml
<?xml version="1.0" encoding="UTF-8"?><preferences stamp="2">
    <com.4d>
        <database>
            <cache flush_buffer_delay="20s" size_maximum="4000"/>
        </database>
    </com.4d>
</preferences>
```

- ユーザー設定：データベースフォルダー内（「Settings」フォルダーの中）にあるファイル
- データファイルのユーザー設定：データファイルと同じ階層（「Settings」フォルダーの中）にあるファイル

キャッシュ設定の構成について詳しくは、ドキュメントを参照してください：

https://developer.4d.com/docs/20/Desktop/user-settings

## 4Dコマンドによるキャッシュ値の取得

### GET MEMORY STATISTICSを使用する

**GET MEMORY STATISTICS**（4D v13で**GET CACHE STATISTICS**から名称変更、20 R7以降は**MEMORY STATISTICS**に名称変更）。このコマンドは、4D/4D Serverのメモリ使用量とキャッシュ使用量に関する情報を提供します。

**GET MEMORY STATISTICS** (info type ; arrNames ; arrValues ; arrCount)

| 引数 | 型 | | 説明 |
|---|---|---|---|
| infoType | 倍長整数 | 入力 | 取得する情報の種類を指定する定数の和 |
| arrNames | テキスト配列 | 出力 | 値の種類の名前 |
| arrValues | 実数配列 | 出力 | 情報の値 |
| arrCount | 実数配列 | 出力 | その情報に該当するオブジェクトの数（利用可能な場合） |

infoType引数は1です（最近のバージョンの4Dでサポートされている唯一の値）。

> 1 – ランタイムエクスプローラーに表示されるような、メモリの一般情報（物理メモリ、仮想メモリ、空きメモリ、使用中のメモリ領域など）

利用可能な情報を取得する例：

```4d
GET MEMORY STATISTICS(1 ; arrNames ; arrValues ; arrCount) // MEMORY STATISTICS 20R7
```

これにより、キャッシュの合計サイズ、キャッシュの使用サイズ、キャッシュ内のブロック数などが返されます：

| arrNamesの値 | 配列の値の説明 |
|---|---|
| cacheSize | データベースの最大キャッシュサイズ。これは実際に割り当てられたキャッシュであり、設定した値と一致しない場合があります。 |
| usedCacheSize | 現在使用されているキャッシュの量。 |
| Physical Memory Size | マシンのRAMの合計。 |
| Free Memory | マシンの空きRAM（OSの報告値）。 |
| Used physical memory | 4Dが使用しているRAMの量（WindowsではWorking Set、Mac OS XではReal Memoryとして報告される値） |
| Used virtual memory | （4D 19R5以降は、はるかに多くの仮想メモリが予約されるため、返される値が非常に大きく見えることがあります） |
| Stack memory | すべてのプロセスのスタックサイズの合計 |
| Free stack memory | （Stack memoryと同じ合計値になることがあります） |

### Get database measuresコマンドを使用する（4D v14.3で追加）

**Get database measures**コマンドは、4Dデータベースエンジンのイベントに関する詳細な情報を返します。この情報には、ディスクまたはメモリキャッシュとのデータの読み書き、およびデータベースのインデックス、クエリ、ソートの使用状況が含まれます。

**Get database measures**は、関連するすべての計測値を含む単一のオブジェクトを返します。optionsオブジェクト引数を使用して、返される情報のオプションを設定できます。

返されるオブジェクトの概要：返されるオブジェクトには"DB"という名前のプロパティが1つだけ含まれ、その基本構造は次のとおりです：

```json
{
    "DB": {
        "diskReadBytes": {…},
        "cacheReadBytes": {…},
        "cacheMissBytes": {…},
        "diskWriteBytes": {…},

        "diskReadCount": {…},
        "cacheReadCount": {…},
        "cacheMissCount": {…},
        "diskWriteCount": {…},

        "dataSegment1": {…},
        "indexSegment": {…},

        "tables": {…},
        "indexes": {…}

    }
}
```

#### 基本プロパティ

基本プロパティは、DBオブジェクトのさまざまな階層にあります。同じ情報を返しますが、対象となる範囲が異なります。基本プロパティの説明は次のとおりです：

| 名前 | 返される情報 |
|---|---|
| diskReadBytes | ディスクから読み込んだバイト数 |
| cacheReadBytes | キャッシュから読み込んだバイト数 |
| cacheMissBytes | キャッシュにヒットしなかったバイト数 |
| diskWriteBytes | ディスクに書き込んだバイト数 |
| diskReadCount | ディスクからの読み込みアクセス数 |
| cacheReadCount | キャッシュからの読み込みアクセス数 |
| cacheMissCount | キャッシュにヒットしなかった読み込みアクセス数 |
| diskWriteCount | ディスクへの書き込みアクセス数 |

### Cache infoコマンドを使用する（4D v16で追加）

**Cache info**コマンドは、現在のキャッシュの内容（使用メモリ、読み込まれているテーブルやインデックスなど）に関する詳細な情報を含むオブジェクトを返します。

**注：**このコマンドはローカルモード（4D Serverおよび4D）でのみ動作します。リモートモードの4Dから使用してはいけません。

デフォルトでは、返される情報は実行中のデータベースのみを対象とします。省略可能なdbFilterオブジェクト引数で、コマンドの対象範囲を指定できます：

- "dbFilter"属性に"All"を渡すと、コンポーネントを含む、実行中のすべてのデータベースのキャッシュ情報を取得します。
- "dbFilter"属性に""（空の文字列）を渡すと、カレントデータベースのみの情報を取得します（dbFilter引数を省略した場合と同じです）。

**Cache info**コマンドは、キャッシュに関連するすべての情報を含む単一のオブジェクトを返します。返されるオブジェクトの基本構造は次のとおりです：

```text
{
    "maxMem": 最大キャッシュサイズ（実数）,
    "usedMem": 現在のキャッシュサイズ（実数）,
    "objects": [...] 現在キャッシュに読み込まれているオブジェクトの配列
}
```

**$info**：4D Serverのキャッシュに現在保存されているエンティティセットと、ユーザーセッションに関する情報を返します。RESTのドキュメントを参照してください：

https://developer.4d.com/docs/20/REST/info

説明

プロジェクトでリクエストを呼び出すと、次のプロパティの情報が取得されます：

| プロパティ | 型 | 説明 |
|---|---|---|
| cacheSize | 数値 | 4D Serverのキャッシュサイズ。 |
| usedCache | 数値 | 4D Serverのキャッシュのうち使用されている量。 |

*注：4D Serverで多数のプロセスが実行されている場合、返されるオブジェクトは非常に大きくなることがあります。このコマンドは、チューニングやサポートの目的で使用することをお勧めします。*
{: .note}

> Function.**flushAndLock**()：**.flushAndLock()**関数は、ローカルデータストアのキャッシュをフラッシュし、他のプロセスがデータベースに対して書き込み操作をおこなえないようにします。データストアは一貫性のある凍結状態に設定されます。たとえば、アプリケーションのスナップショットを実行する前に、この関数を呼び出す必要があります。

## 4D_Info_Reportによるキャッシュの監視

4D_Info_Reportコンポーネントは、長年にわたって更新されてきた、現在もメンテナンスされているコンポーネントです。最新のバージョンおよび今後のバージョンの4Dに対応しています。このコンポーネントは、サーバーの状態のスナップショット（単一のレポート）として、あるいは履歴や推移を分析するためにストアドプロシージャーで一連のレポートとして、人が読めるテキストレポートを作成します。

- このコンポーネントを使用する利点：サーバーをサービスとして、またはヘッドレスモードで実行している場合でも、リモートの（Administrator）ユーザーが、実行中のデータベースの推移をリアルタイムで確認できます。そして、表示されたポリゴンをもとにキャッシュ設定などを後から調整したり、メモリリークを示したりできます。

Folder_reports（作成されたレポートを保存するフォルダーのデフォルト名）のアーカイブを、他のスタッフやテクニカルサポート担当者に渡して分析してもらうことができます。

1つのレポート（人が読める形式）から、4Dまたは4D Serverの実行コンテキストに関する多くの情報が得られます。

このコンポーネントはGitHubで入手できます：https://github.com/4d/4D_Info_Report/releases/latest/

（旧バージョンの4D用のコンポーネントのアーカイブも、GitHubのリンクから入手できます。）

このコンポーネントには基本的なグラフィックインターフェースが組み込まれており、保存されたレポートをもとにサーバーで記録された値の推移や、情報／注意の内容を表示できます。たとえば、サーバーが稼働中で、コンポーネントが組み込まれている場合は、リモートアプリケーションで表示できます。

## その他のキャッシュ：ORDAキャッシュ

4Dリモートアプリケーションは、dsコマンドでメインデータストアにアクセスする際にORDAを使用します。なお、4Dリモートアプリケーションは従来の方法でデータベースにアクセスすることもできます。これらのアクセスは、4Dアプリケーションサーバーが処理します。

その他の4Dアプリケーション（4Dリモート、4D Server）は、Open datastoreコマンドでリモートデータストアのセッションを開きます。これらのアクセスは、HTTP RESTサーバーが処理します。ドキュメント：https://developer.4d.com/docs/20/ORDA/datastores/

ORDAを使用する場合のために、（リモートコンピューター上の）限定的なリモートキャッシュが導入されています。ドキュメント：https://developer.4d.com/docs/20/ORDA/datastores#orda-cache

### ORDAキャッシュ

最適化のため、ORDAを介してサーバーに要求されたデータは、ORDAリモートキャッシュ（4Dのキャッシュとは別のもの）に読み込まれます。ORDAキャッシュはデータクラスごとに構成され、30秒後に期限切れになります。

タイムアウトに達すると、キャッシュに含まれるデータは期限切れとみなされます。期限切れのデータにアクセスすると、サーバーにリクエストが送信されます。期限切れのデータは、領域が必要になるまでキャッシュに残ります。

デフォルトでは、ORDAキャッシュは4Dによって透過的に処理されます。ただし、次のORDAクラス関数を使用して内容を制御できます：

- dataClass.setRemoteCacheSettings()
- dataClass.getRemoteCache()
- dataClass.clearRemoteCache()

## まとめ

4Dのキャッシュは、4D Serverのパフォーマンスにおいて重要な役割を担っています。キャッシュの使用効率に影響するその他の要素として、ハードウェア構成（コンピューターの利用可能なメモリ、ストレージの種類、ネットワークアクセス）やデータベースの設計などがあります。本テクニカルノートは、キャッシュ設定と観察のために可能な操作、そして最近のバージョンの4Dまでにキャッシュ管理の何が変わったかについて、最新の情報をまとめたものです。
